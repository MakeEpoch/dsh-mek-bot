## 1. 为什么

用户希望每个 Bot、每个群都有持续维护的待办，能够安排之后再做的工作、按前置条件接续，以及定时执行。现有执行记录主要描述已经开始的协作，不能直接充当包含未启动工作、依赖关系和周期规则的长期待办。

用户通过聊天交代目标，群管理员负责拆分、安排成员、处理问题和检查结果。用户不需要创建项目、填写负责人或手动维护任务流程。系统承担事件记录、条件判断、排队、状态同步和恢复。

### 1.1 本次讨论确定的产品方向

1. 以个人会话和群为待办范围，第一版不增加项目实体或项目选择步骤。已有“项目知识”继续是资料共享范围，不成为使用待办的前置要求。
2. 一件完整事情对应一个主 task；管理员可将其拆成多个子 task。子任务不能成为互不关联的几条群待办。
3. 群管理员天然承担本群任务的协调职责。用户无需标记负责人、执行者或验收人；内部仍记录实际派工与检查者，以便恢复和追溯。
4. 前置依赖与主子层级分开：层级描述工作拆分，依赖描述何时允许执行。
5. 个人列表和群列表可以展示同一项工作，展示位置不产生新的任务副本。
6. 定时规则每次触发产生独立的执行事项；提醒与自动执行的含义明确区分。
7. 正常工作安静推进。只有有用的结果、需要用户决定的问题和无法自行解决的阻塞才通知用户。
8. 不改变 DSH 的工具授权、凭据和宿主边界，不以管理员身份代替用户授权。

本文进一步给出默认策略、数据关系和验收要求。并行数、重试预算继续服从已有执行策略；本文不新增一组必须由用户配置的参数。

## 2. 当前能力与拟新增能力

下表只说明上述源码基线中可定位的机制，不表示本设计的流程已经联通或通过验收。

| 方面 | 当前基础 | 本设计增加的部分 |
|---|---|---|
| 执行协调 | `mek-coordination.js` 保存 root、work、决策和投递记录；支持结果检查、返工与取消 | 尚未执行的待办、稳定子任务身份、显式依赖、等待与排队 |
| 群协作 | 已有群管理员、成员 Session、群委派与结果聚合 | 群内新需求默认由管理员建立主任务并安排，不将普通发言视为派工 |
| 个人与团队展示 | `mek/tasks.jsx`、团队概况展示执行记录与重要动态 | 个人/群待办视图、主子任务折叠、等待原因、同一任务的多处投影 |
| 定时 | `schedules.js` 适配可选的 DSH `schedule` 服务，创建面向 Session 的提醒并支持换段迁移 | 逻辑规则身份、触发实例去重、与主任务关联、重叠和漏跑策略 |
| 定时入口 | 原生 `mek/view.jsx` 当前将 `actions.schedules` 隐藏 | 会话待办内提供上下文入口；不恢复独立应用的全局调度菜单 |
| 复用流程 | 已有版本化流程、验证和显式运行 | 作为定时执行内容的可选复用方式，不要求普通待办先建立流程 |
| 资料范围 | 项目知识和可选 `projectId` 已存在 | 保持兼容，不据此自动授予待办或私聊访问权限 |

“等待前置”“定时后结构化派工”“群管理员交接”均为本方案要实现的行为。现有接口可作为适配入口，不能据此宣称新功能已存在。

## 3. 用户体验与完整例子

### 3.1 普通群任务

用户在研发群说：“修复登录问题，修好后检查登录和注册流程，通过后再发布。”

```text
主任务：修复登录并完成发布
├─ A：Coder 定位并修复登录问题
├─ B：Tester 检查登录和注册流程    等待 A 检查通过
└─ C：执行发布                    等待 B 检查通过
```

管理员一次简短确认，说明已安排的工作。A 执行并返回证据，管理员检查通过后 B 才能进入执行队列。B 发现问题则在 A 的原子任务中返工；C 继续等待。全部必要工作通过检查后，管理员在原群交付结果并结束主任务。发布仍遵守用户原始范围与 DSH 授权。

列表默认展示一条主任务。展开后显示子任务、执行成员、等待原因和结果；派工历史进一步折叠。

### 3.2 先记录，之后再做

“这个先记下来，下周再处理”创建待办，不启动成员工作。“现在做”立即安排；“明天下午提醒我”只提醒；“明天下午自动处理”按已明确的要求执行。时间或目标存在实质歧义时再补必要问题，不能把提醒解释为工作授权。

### 3.3 个人任务

私聊 Bot 接到任务，由该 Bot 协调和检查，可以自行执行或沿用已有委派。个人列表同时展示自己的主任务和群里分配给自己的子任务，二者有清楚的来源标记。

群子任务是引用，不另建个人主任务。私聊中的独立事项不自动出现在群里。

## 4. 任务模型与身份

### 4.1 三层记录

| 记录 | 含义 | 稳定性 |
|---|---|---|
| 主任务 | 用户交代的一件完整事情，保存目标、范围和交付要求 | 跨轮次、重启、Session 换段保持相同身份 |
| 子任务 | 管理员拆出的一个可安排、可检查的工作单元 | 返工或更换成员不改变子任务身份 |
| 派工记录 | 一个成员对某个任务的一次执行尝试 | 每次重新执行生成新记录，链接此前尝试 |

没有必要拆分的小任务允许直接在主任务下产生派工，不强制创建同名子任务。界面默认两层；成员需要继续协作时，由管理员在原主任务内安排。底层已有嵌套委派可以保留追溯关系，不新增独立主任务或无限展开的用户操作树。

Superagent 的 Ticket / Assignment 提供了“工作身份与执行尝试分离”的参考；Assignment 不是子任务。本文的主子任务与依赖是本项目扩展，不能用一次派工替代长期子任务。

### 4.2 最小数据关系（拟定，非已实现 schema）

| 对象 | 需要保存的信息 |
|---|---|
| 任务 | `id`、`rootId`、可选 `parentId`、标题与目标、完成要求、创建来源、逻辑会话范围、状态、修订号与时间 |
| 任务范围 | `botId` 或 `roomId`；以长期身份定位，不使用当前 Session id 作为业务主键 |
| 协调记录 | 协调 Bot、群管理员任期标识、当前安排版本；由系统维护，不要求用户填写 |
| 派工 | `assignmentId`、任务 id、成员 Bot、实际 Session、安排版本、尝试序号、输入版本、结果、证据与工具投递身份 |
| 依赖 | 后继任务 id、前置任务 id、要求的检查结果、当前满足的结果版本 |
| 人工问题 | 问题 id、所属任务与派工、具体问题、答复目标、当前状态；安全凭据沿用现有独立通道 |
| 定时规则 | 规则 id、逻辑会话、动作种类、时间与时区、启停状态、内容版本、宿主调度绑定 |
| 触发实例 | 规则 id、计划发生时间、规则版本快照、实例 id、关联主任务或提醒、派发/跳过/未知结果 |
| 事件与待执行动作 | 来源事件身份、任务/规则修订号、动作身份、持久化与投递结果，用于去重和恢复 |

标题和正文可修改，身份不随重命名改变。任务来源记录足以跳回原消息，不能把用户私聊全文复制到群任务。结果保留产物所属 Session 和版本，不能用当前成员 Session 代替实际产物来源。

## 5. 新建、补充与消息接续

### 5.1 管理员判断，系统校验

| 输入 | 处理 |
|---|---|
| 新的完整工作要求 | 新建一个主任务；需要时拆子任务 |
| 原目标内的补充 | 更新原任务的要求和安排，必要时增加子任务 |
| 询问进展、普通讨论或成员公告 | 不自动创建任务 |
| 暂停、继续、取消 | 对明确指向的任务操作 |
| 与原目标独立的新要求 | 建立新主任务；不能仅因同群或同成员而合并 |
| 引用外部资料、工具输出、CI 或 Bot 消息 | 作为事实或触发信号；不自动取得扩大工作范围的权限 |

优先依据任务卡片、回复链、来源消息关联定位任务，其次结合上下文判断。多个目标均合理时问一个具体问题。不依赖标题相似度或“当前群只有管理员”强行归类。

明确提出的工作无需重复征求已授予的许可。系统先检查身份、范围、取消状态和版本，模型负责理解目标与分工；模型不能修改权限校验结果。

### 5.2 后续消息的边界

同一群可存在多个独立主任务。消息只送到明确相关的任务，不能将整个群订阅为所有任务的完整输入。成员只收到本次派工所需的目标、上下文、约束和前置结果。

原范围内的补充继续原任务；越出范围则由管理员建立新工作安排。已完成任务收到明确的相关修改要求，可以重新打开同一主任务并保留旧交付；纯感谢或状态询问不重新启动工作。

用户明确取消产生持续的停止约束。Bot 回复、定时事件、CI 或新线索不能解除；只有用户明确恢复或重新要求工作时才处理，且重新检查原范围和执行条件。

## 6. 管理员、成员和权限

### 6.1 默认协调规则

群内发起的新主任务归属该群，由当前管理员 Bot 协调。私聊发起的主任务继续由原 Bot 协调。群管理员无需是 Main Bot，协调权也不包含提升沙盒权限或获得私聊访问权。

私聊主任务委派到群时，沿用原主任务和原联系者的交付责任。群管理员负责被委派部分的成员安排，将问题和结果返回原任务，不另起一条群主任务，也不把整个私聊公开。只在明确授权的群范围显示必要的委派摘要。

这是对既有“原联系 Bot 持有任务”契约的有界扩展：新增群内任务由群管理员承接，不追溯改写已有私聊、跨群或历史任务的所有权。

### 6.2 分工与接替

管理员选择合适成员、设置依赖、处理成员问题并检查结果。成员自行选择范围内的实现方法；需要进一步拆分、额外成员或调整依赖时向管理员提出，不能自行扩大主任务。

成员只能报告其有效派工的结果，不能自行宣告整个主任务完成、移除前置条件或将自己的证据视为管理员验收。用户仍可直接修改安排或处理必要问题。

群缺少有效管理员时，新任务可被记录，但停止自动派工，显示“等待设置群管理员”。不暗中选择任意成员代管。

更换管理员时，系统先使旧任期的协调写入和新派工失效，再把目标、依赖、运行中派工、结果和未决问题交给新管理员。运行中的成员工作继续保持同一派工；已在途动作须核对，不因交接重发。旧管理员的迟到安排被拒绝，仍有效的成员结果由新管理员检查。

成员退出或删除后，管理员接替其未完成事项；先核对原派工和资源，不能以成员不可用为由重复已完成或结果未知的外部动作。删除群或归档会话会冻结相应自动触发，历史按现有删除/隐私规则处理，不将工作静默转到其他群。

## 7. 生命周期、结果和用户状态

### 7.1 用户看到的状态

| 状态 | 含义 |
|---|---|
| 待办 | 已记录，尚未开始；可附“等待前置”“等待约定时间”“排队中” |
| 处理中 | 已开始安排或执行；可附“管理员检查中”“等待成员回复”等原因 |
| 已完成 | 已满足目标，必要结果通过检查，无未决工作 |
| 已取消 | 用户放弃或明确取代该事项，保留历史 |

暂停作为独立控制标识展示，不伪装成完成。需要用户决定、授权、凭据或核对结果时，显示独立的行动提示。失败和阻塞必须可见，不能一直显示“正在执行”；已完成部分保留。

底层保留现有细分状态，并按确定优先级生成展示：已取消/已完成 → 暂停 → 需要用户行动 → 失败或未知需处理 → 等待条件 → 排队 → 实际执行 → 结果检查。群成员的普通问题先由管理员处理，不直接变成用户待办。

### 7.2 派工结束不等于工作完成

一次轮次结束、让出发言位、后台命令启动或单条消息返回，都不能自动结束任务。派工必须报告结果、证据、产物和仍在运行的后台工作；有后台工作则继续记录其状态，不提前释放实际资源。

管理员通过检查后，发布带版本的子任务完成事实，后继才可被唤醒。必要结果不完整、缺报告、存在未知投递、未决问题或失败时，主任务不能完成。缺证据时优先补报告或验证，不重复已经完成的外部动作。

普通事项由管理员完成检查与交付，不增加用户逐条点击验收的流程。只有原需求明确要求用户确认、或者必须由用户作出的决定，才等待用户。

### 7.3 改动、暂停、取消和返工

| 操作 | 规则 |
|---|---|
| 补充要求 | 保存新修订；原范围内调整待执行安排，运行中的派工收到明确的变更输入 |
| 返工 | 保留子任务身份，新增派工尝试并链接此前结果；已完成但需重新验证的部分单独安排 |
| 暂停 | 先停止新派发和自动唤醒；对当前派工按 DSH 能力请求停止，并准确显示仍在运行或结果未知的动作 |
| 继续 | 解除相应暂停，核对已有进度和未知结果，再重新检查条件 |
| 取消 | 禁止后续派工，撤销尚未执行的动作；对运行中动作请求停止，保留记录，不承诺回滚已有外部效果 |
| 调整子任务 | 保存管理员理由；删除依赖、替换前置或缩减工作必须符合原目标，重大范围变化回用户决定 |

被取消的必要子任务不能算作成功。管理员可将已被替代或不再适用的子任务显式标记为“不再计入本次交付”，说明替代任务或理由；该决定不能绕过用户要求或掩盖失败。

## 8. 前置依赖与条件执行

### 8.1 第一版语义

第一版支持同一逻辑个人/群范围内的任务依赖，可以引用同一主任务的子任务，也可以引用同范围的其他任务。跨群、跨私聊依赖暂不提供，现有委派的父子回流不因此失效。

所有前置都必须通过检查，后继才具备执行资格。依赖主任务表示等待其整体完成；依赖子任务表示等待该工作结果。主子关系本身不规定子任务间顺序。

```text
A：接口修改 ──┐
              ├─→ C：联调验证
B：页面修改 ──┘
```

条件满足、未暂停、未取消、授权范围仍有效、成员与资源可用，是开始派工的共同条件。满足前置只进入可执行队列，不保证立即开始。

### 8.2 状态变化的处理

| 前置状态 | 后继行为 |
|---|---|
| 未开始、执行中、等待检查 | 等待，不占成员执行名额 |
| 已通过检查且结果版本有效 | 记录满足版本，重新检查派工条件 |
| 失败、阻塞、返工中 | 继续等待；由管理员处理原任务 |
| 已取消、被删除或不可读取 | 标记“前置无法满足”，停止自动启动，交管理员处理 |
| 投递或外部结果未知 | 先核对，不视为成功或失败，不盲目重跑 |

系统检查依赖图，拒绝自己依赖自己、循环、以及子任务等待包含自己的主任务完成。循环检查同时纳入“子任务完成才可完成主任务”的聚合关系，不能只检查显式依赖边。

任务改名不改变关联。用户使用自然语言指定前置时，管理员必须解析到稳定任务 id；歧义、不可见或失效的目标不能保存成可执行条件。

### 8.3 结果版本与返工

派工记录其使用的前置结果版本和产物版本。前置重新打开或结果失效时，尚未启动的后继撤销原就绪资格；启动前再次核对版本，避免就绪后、实际执行前的竞态。

后继已经运行时，由管理员判断暂停、接收新输入或在其后安排验证，不能仅修改状态就宣称运行已停止。后继已经完成时保留旧结果，并显示其基于旧版前置；管理员决定是否重新验证。不会静默回滚或自动重复发布。

同一次有效前置满足只产生一次就绪转换。撤销后再满足时使用新版本身份，不复用已过期的待执行动作。

### 8.4 等待方式

条件等待保存在宿主状态中，不维持模型轮次，不让管理员用循环、`sleep` 或反复询问等待成员。任务完成、时间到达、管理员交接和资源释放等事件触发确定性复核；定期恢复扫描只修复遗漏，不重复创建模型工作。

第一版不提供任意脚本条件、任意网页变化轮询或通用布尔表达式编辑器。外部 CI、审批等条件以后通过有来源的适配器接入，不能让模型一句“应该通过了”替代实际事件。

## 9. 定时规则与每次触发

### 9.1 三种动作

| 类型 | 到点行为 | 是否启动执行 Bot |
|---|---|---|
| 提醒 | 在原会话给出一条明确提醒，关联原待办时不重建任务 | 否 |
| 周期待办 | 每期创建一个待办主任务，等待安排 | 否 |
| 自动执行 | 每期创建一个主任务，由当前 Bot 或群管理员安排 | 是，条件满足后启动 |

默认支持单次、每天、工作日、每周；时区为 `Asia/Shanghai`，显示下次发生时间。相对日期在保存时解析为明确时间，保留用户原表达供查看。无需先建立项目或可复用流程；重复的复杂工作可绑定已有已验证流程版本。

### 9.2 规则不是永不结束的主任务

```text
规则：每周五 16:00 整理本群进展
├─ 2026-11-06：一条主任务及其子任务、结果
├─ 2026-11-13：另一条主任务及其子任务、结果
└─ 下次：2026-11-20 16:00
```

规则编辑只影响后续实例；已经产生的实例保存当时内容版本，不静默改写运行中目标。规则暂停只阻止后续实例，停止当前执行需单独处理。一次周期的失败不自动永久关闭规则；无法投递、目标失效或持续需要人工恢复时，显示明确问题，避免每期制造重复通知。

触发唯一性以规则逻辑 id 和计划发生时间确定，并保存当时规则版本。同一次计划发生时间的修订、Session 换段或宿主回调重送不得产生两个实例。时间计划改变后，未派发的旧动作按版本失效规则处理，不能借新版本重新执行已经发生的一期。

### 9.3 默认重叠与漏跑策略

| 情况 | 默认行为 |
|---|---|
| 上一期执行、等待检查、暂停或阻塞，尚未结束 | 跳过本期并记录原因，不累积自动执行任务 |
| 周期待办上期仍未完成 | 跳过本期，保留已有待办；用户可明确要求每期独立生成 |
| 提醒规则 | 每期按提醒语义处理，不把未读提醒视为运行中执行任务 |
| 服务离线错过周期 | 记录错过，不连续补跑；用户明确选择时可补最近一期 |
| 单次自动执行时间已过而系统当时离线 | 显示“已错过，待处理”，不在未知时效下静默执行 |
| 规则目标或群管理员失效 | 暂停派发，提示目标问题，不改发其他会话 |
| 开始结果未知 | 对账恢复，不能用“重试”再建立一条主任务 |

“明天 09:00 后，回归通过再发布”表示时间与前置都满足。时间到了仍未通过就继续等待；通过得早也等到约定时间。截止时间与开始时间分开，逾期提示管理员，不自动取消、忽略依赖或强制执行。

待办截止时间用于说明交付期望，不能静默覆盖已有执行策略中的硬期限、预算和审批限制。若已配置硬期限，到期后的新执行仍由原 guard 拒绝，管理员需要调整合法安排；不能因本文规定“逾期提示”而绕过该限制。

周期规则引用前置时，默认引用该期实例内的任务；确需固定外部前置时必须明确绑定任务与结果版本，不能让上一期成功自动满足本期检查。

### 9.4 复用 DSH 调度

DSH 拥有时钟和计划唤醒，插件拥有业务规则、触发实例和任务关联。实现时通过公开服务适配，不新建第二套常驻调度器或后台计时进程。

规则绑定长期 Bot / room 身份，实际触达时再解析当前 Session。Session 换段、旧调度记录复制/删除和恢复期间仍以插件的逻辑实例身份去重，不依赖宿主调度记录 id 永久稳定。

必须先核对当前 DSH 公共服务的更新、暂停、回调身份和启动能力。若宿主只能投递提醒文本，应设计可校验的结构化桥接并验证端到端身份，不让模型自由转述文本承担唯一的去重与派工保障。能力不足则准确标明不可用，不能修改 DSH 或用未公开内部接口补齐。

## 10. 并发、工作区和持久恢复

### 10.1 空闲等待与实际资源分开

等待前置、时间或用户答复不占用成员执行名额；尚在运行的工具、后台进程和不明确的资源占用继续保持实际资源约束。释放模型名额不等于释放文件、浏览器或账号。

正常就绪任务按进入就绪队列的时间安排。同一 Bot 的重叠执行仍服从 DSH Session 和现有任务并发策略；必要的人类答复、停止和状态请求不能被新任务无限挤压。控制操作能优先处理，不代表可以突破资源互斥执行修改。

已有策略的“开放委派数量”与实际执行名额分别计算。尚未派工的等待项不创建占位 work；已经派工后等待问题的工作可释放实际执行名额，但不能通过删除开放 work 绕过原有协调上限。实现时明确两种计数与用户可见原因，不能只在 UI 中隐藏等待项就宣称释放了资源。

沿用现有资源租约与背景工作生命周期。同工作区、文件或账号冲突时排队或由管理员隔离工作目录；对支持的代码工作可使用独立 worktree，不将所有工具调用强制迁到新 Session。租约是协调手段，不是 OS 隔离，不能推断任意 shell 后台进程已停止。

### 10.2 先记录，再派工

任务安排版本、就绪转换、派工意图和 outbox 写入同一个持久化提交，再执行实际投递。多个并发唤醒争用同一任务时，以任务修订和派工身份校验保证一个有效尝试。新增或接替派工检查当前管理员任期，成员执行检查其派工是否仍有效；管理员更换本身不使已在运行的有效派工失效。开始工具前再次检查取消、暂停、适用的前置版本与授权范围。

报告须携带任务与有效派工身份。过期尝试的迟到报告保留审计，但不能覆盖当前结果或满足后继条件。一个失败回调不等于外部动作未发生，未知结果先通过已有 inbox、历史或外部凭据核对。

不能承诺网络和任意外部系统的“绝对只执行一次”。保证的是内部身份去重、确定的状态转换和保守恢复；外部系统支持幂等键时继续传递该身份，否则未知时停止自动重放。

### 10.3 重启与数据演进

重启恢复未结束任务、依赖、定时实例和待执行动作，核对旧派工是否已经进入历史或完成。已完成的子任务不重派；等待项重新计算条件；运行中断或投递不明的项先进入核对。用户的暂停和取消约束持久保留。

沿用本地团队状态与现有单写入/持久化机制，新增字段或模块使用明确版本。未知未来版本拒绝覆盖，不能遇到解析错误便重置任务清单。

历史 root 和 work 身份保留，新增稳定任务/子任务与派工的映射。不得把已有每个 work 或 group 聚合机械转成独立待办；无法可靠推导的历史只作为执行历史展示。旧已完成/取消记录不重新打开，旧待处理工作按旧契约继续；新模型分阶段接入，不要求一次破坏性迁移。

记录随长期 Bot / room 身份存活，当前 Session 换段不丢失。归档、清理和删除服从隐私规则；第一版不做自动清除未决记录，实施时需要评估现有状态文件增长和分页，不能默认无限将所有历史装进 feed。

## 11. 原生界面与通知

保留一个 DSH Bot 入口和当前顶部 Bot/群导航。当前会话内提供“对话 / 待办”轻量切换或等价的局部入口；个人/群选择决定默认范围，不增加全局项目栏或第二套任务应用。

### 11.1 待办页

- 先展示需要用户行动的事项，再展示当前主任务、未开始事项和已完成历史；常规问题由管理员处理。
- 默认只列主任务，展开后展示子任务与依赖。个人“分配给我的”区域可直接显示来自群的子任务，并链接主任务。
- 数量与实际筛选列表一致；失败、未知、暂停和等待原因使用明确文字，不编造完成百分比。
- 详情包含目标、子任务结果、必要证据和来源跳转；派工次数、内部 id、投递过程默认折叠。
- 消息可“加入待办”或“关联已有任务”；已有普通聊天不会因入口出现自动成为任务。
- 定时规则在同一会话待办中显示动作、下次时间、最近结果与启停；不恢复上游全局 Bot 调度菜单。
- 等待前置显示具体事项，例如“等待：接口修改、页面修改”，能跳到有权查看的前置任务。

文中中文为产品语义，实际落地沿用现有语言系统与英文默认文案，不另建一套语言或组件体系。宽屏与 390px 均需可用，所有 DOM、弹窗、坐标和样式留在原生 Bot 场景内。

### 11.2 通知与人工问题

接单简短确认一次；正常派工、轮次结束、前置满足、内部返工和普通排队只更新卡片。完成时在原会话交付一次结果。原任务联系人不必跳到执行成员窗口追问。

管理员先处理常规问题。确需用户时提出一个具体、可行动的问题，使用现有结构化卡片；安全凭据和工具审批继续使用对应通道。人工问题不以自由文本猜测生成，也不夹在一大段内部报告中。

只有问题性质变化、到达明确约定的提醒时间、用户直接询问或新的可用结果出现时再次通知。重启、重复事件和刷新不能重发同一条未变化通知。共享摘要开关与隐私 Bot 限制仍有效；任务共享不是读取无关私聊的依据。

## 12. 实现边界与模块分工

以下是拟定职责，不承诺已经存在同名接口或文件。先检查现有模块能否承接，再决定是否拆文件。

| 职责 | 建议承接位置 | 必须保持的契约 |
|---|---|---|
| 任务、子任务和派工映射 | `src/host/mek-coordination.js` 及必要的局部模块 | root/work 与原联系者回流、结构化检查、返工及取消继续有效 |
| 群内任务接入与管理员协调 | `src/host/groups.js`、协调器钩子 | 普通成员公告不触发委派；群内任务与普通 relay 区分 |
| 依赖检查和就绪转换 | 协调器中的确定性模块 | 无循环、版本有效、等待不占模型执行资源 |
| 定时业务适配 | `src/host/schedules.js` 与 DSH 公共服务 | 一个时钟来源、逻辑实例去重、当前 Session 解析 |
| 摘要、问题和通知 | `src/host/mek-team.js` 与已有决策/outbox | 共享权限、明确人工问题、通知去重和原会话交付 |
| 权限、预算、并发与资源 | 既有执行策略和租约模块 | 所有新启动路径通过原 guard，不以任务功能绕过 |
| 会话投影与操作 | 已认证 `api/bot` channel、共享 feed | 宿主校验修改权限和修订号，不只靠 UI 隐藏按钮 |
| 用户界面 | `src/client/mek/` | 原生布局、任务投影不复制实体、不侵入 DSH 主会话 |

模型工具只表达创建/补充任务、安排成员、设置前置、报告、检查和控制等业务意图，宿主验证权限与状态。最终工具名和 schema 在实现阶段核对现有工具后确定，避免同一动作出现多个重复入口。

查看、等待和按事件更新不必启动模型。管理员处理合并后的必要事件，避免每个底层工具事件都唤醒一次管理员。任务实际执行继续用 DSH 的公开能力，不引入原型的独立 worker 预设、自动放行权限或临时 subagent 能力。

## 13. 分阶段交付

| 阶段 | 范围 | 交付门槛 |
|---|---|---|
| P1：主子待办 | 个人/群范围、先记录与立即执行、管理员分配、稳定子任务、个人引用视图、报告检查、暂停取消 | 一个群需求对应一个主任务；原私聊回流和权限保持，重启不丢状态 |
| P2：前置依赖 | 同范围依赖、循环校验、结果版本、事件唤醒、排队和返工失效 | 前置不满足不派工；有效完成只唤醒一次，取消/返工竞态可恢复 |
| P3：定时 | DSH 接口核对、提醒/周期待办/自动执行、逻辑规则与实例、重叠和漏跑 | 实际候选包在隔离 DSH 验证定时、换段、重启与不重复执行 |
| 后续扩展 | 受控外部条件、复杂流程复用、观察模式的主动建议 | 明确来源、授权、噪声预算和独立验收，不作为前三期前置 |

P1 的数据关系即区分任务和派工，并预留来源、版本与触发关联，避免 P2/P3 重建所有业务身份。不在 P1 宣传未交付的依赖或定时功能。

每期实现同步更新根/包内 README、相关契约及 [UI 测试方案](../dev/mek-ui-testing.md)，准确标注当前能力。本文仅新增设计，不替换现有功能清单，也不改变当前版本的行为说明。

| T13 | 无管理员、更换管理员、旧安排晚到 | 无管理员不派工；交接后单一有效协调者，不重启已有成员工作 |
| T14 | 移除正在执行的成员 | 核对旧派工，再接替；未知外部动作不重复 |
| T15 | 返工和缺验证证据 | 保留原子任务和结果，新尝试有独立 id；主任务不提前完成 |
| T16 | 模型轮次结束但后台工作仍运行 | 任务与实际资源保持正确状态，不误判完成 |
| T17 | 同 Bot 多任务、同工作区并发 | 排队公平，资源互斥，等待前置不占执行名额 |
| T18 | 每期提醒、周期待办、自动执行 | 三种动作分别按定义处理，无隐式升级 |
| T19 | 同一期回调重送、规则修订、换段迁移 | 至多一个有效触发实例与主任务 |
| T20 | 上期未完成与服务离线 | 按默认策略跳过/记录，不积压补跑，单次错过可处理 |
| T21 | 时间和前置共同限制 | 两者都满足才排队，过期不绕过条件 |
| T22 | 本期依赖与上期成功结果 | 不串期，实际输入版本正确 |
| T23 | 重启发生在持久化、投递、接收、报告之间 | 保留身份并恢复；对账未知，不重复外部动作 |
| T24 | 取消后自动事件或 Bot 追问 | 保持停止；只有明确用户恢复才重新安排 |
| T25 | 群/会话删除与 Session 换段 | 长期任务身份稳定；失效目标不改发其他会话 |
| T26 | 普通进展、重复错误、必要问题与交付 | 常规安静，问题可行动，重复通知被去重 |
| T27 | 900/700/390px、主题、会话切换 | 导航、列表展开、条件跳转和卡片可用，无场景外泄漏 |
| T28 | 未授权任务访问、伪造成员报告、旧管理员写入 | 服务端拒绝，不能仅依赖前端限制 |
| T29 | 旧任务、旧完成记录和未来 schema | 历史不重放，旧工作保持原契约，未知版本不被覆盖 |
| T30 | DSH 无调度服务或仅提供文本提醒 | 准确显示能力限制；桥接未验收不能宣称自动任务已可用 |

完整验收还需检查候选 tgz 的源码/归档/安装一致性，使用独立 `.dsh-test-*` 与本地 mock，不操作正式 DSH 或真实账号。保存源码、bundle、包哈希、环境、执行用例和未验证项。最初设计阶段只写文档；后续实施的实际验证记录单列在文末，不把整张矩阵视为已经通过。

## 15. 不做什么

- 不增加必填项目、负责人表单、用户手动流程编排器或多租户项目管理系统。
- 不将日常讨论、普通群发言和每一次工具调用变成独立待办。
- 不把执行尝试、成员一条回复或结束轮次当作子任务完成。
- 不让 Bot 自己扩大授权、把资料订阅当作新要求，或替用户处理真实工具审批与凭据。
- 不照搬 Superagent 的全部领域概念、GitHub/飞书部署、默认无审批执行方式或独立 worker 生命周期。
- 不新增第二套 DSH、全局 Bot 侧栏、外部调度服务器或任意条件脚本平台。
- 不把相同成员、相似标题或同一 Session 视为任务相同的证据。

## 16. 已知限制与实现前核对项

1. DSH 的公开调度服务是否具备所需的更新/暂停/回调身份和结构化派工桥接，需要以实现时宿主版本核对；源码里的提醒适配不等于本设计已可用。
2. 当前协调器以原联系者和执行中的 root/work 为中心，待办、稳定子任务及群管理员交接要设计兼容映射，不能直接重用一个 work id 表示所有返工。
3. 当前同 Bot/群 Session 可承接不同工作。报告关联、输入隔离和并发 guard 必须先验证，不能以新增待办字段解决执行串线。
4. 任意外部系统不一定支持幂等；后台进程、网络超时和工具中断可能留下未知结果，无法承诺自动重试总是安全。
5. 同范围跨主任务依赖会同时涉及完成聚合与显式依赖，需要统一循环检查和版本失效处理。
6. 第一版的队列和资源协调仍不等于文件系统、账号或操作系统隔离。大型代码并行工作需要合适工作目录及 DSH 策略。
7. 任务与历史数据增长、源消息删除后的跳转和隐私删除行为，需要在实际数据量与现有存储契约下验收。

调度器当前公开能力仍将内部时钟消息投递到原绑定 Bot Session。插件只依据宿主持久投递历史创建业务实例，并拒绝该时钟轮次直接调用工具；自动执行会另外持久通知当前管理员，要求拆分并启动同一主任务。它不是无模型的宿主回调，也不是已验证的任意真实模型自动规划能力。超过计划时间一分钟才送达的实例按本轮保守默认记为错过；不声称实现了完整离线时段重建。

### 复查修正（2026-11-03）

主任务的前置条件现在同时约束所有子任务，循环检查包含这层继承关系。前置返工使已验收后继也失去当前有效资格；旧结果保留，但不能解锁后续派工或通过主任务验收。重新返工需先有当前已验收的前置结果，原有执行工具也不能绕过这些条件。群工具轮次只能控制当前群，派发前再次核对持久对象身份、管理员和写入资格。

定时恢复按计划顺序保留第一条待处理实例，后续回执不能因为同批恢复而绕过重叠保护。未处理的历史回执以及过期的待通知实例不自动补跑；重启遗留的“发送中”标为送达未知，不自动重发。规则绑定记录保留创建时真实 Session，通知前再次核对群管理员。执行结果投递前准备当前管理员的群 Session 并更新返回地址，不能依赖下一次定期恢复才处理交接。复查新增七项回归；实际包与安装结果另见 UI 验收记录。
