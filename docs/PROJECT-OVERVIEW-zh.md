> 依据：仓库 README、docs/vision.zh.md、AGENTS.md 与实际源码（170 个 js 文件，约 4.3 万行）

## 一句话

**在 DeepSeek Harness 里，把「一个人用一个 AI」变成「一支有分工的 Bot 团队」。**

用户跟一个 Bot 提需求，它自己决定派给谁、收回结果、审查、返工，最后统一交付。整个过程用户看得见、能中断、能追责。

---

## 一、它解决什么问题

### 单 Agent 的天花板

DSH 本身已经很强：一个会话里能跑工具、能写代码、能调浏览器。但做复杂项目时有几个绕不过去的问题：

| 问题 | 表现 |
|---|---|
| **上下文会满** | 一个任务做久了，前面的结论被压缩掉，或者干脆开始新会话，之前说过的话就没了 |
| **角色会串** | 让同一个 Agent 既写代码又做验收，它会替自己的代码辩护 |
| **任务会丢** | 长任务做到一半，断开、重启、用户走开，回来时不知道做到哪 |
| **范围会飘** | 没有明确的拥有者，谁都能扩大范围，最后交付一堆没人要的东西 |

### 这个项目的答案

**不是做一个更聪明的 Agent，而是做一套「组织规则 + 持久化状态」。**

每个 Bot 仍然跑在 DSH 的普通 Session 里，用同样的模型、工具、权限。项目做的是：

- 给每个 Bot **长期身份**（名字、职责、模型、工作目录、记忆）
- 给任务**明确归属**（谁接的就归谁，不会半路被抢走）
- 让 Bot 之间能**互相派活**，结果自动回传
- 把关键状态**落盘**，断开重启不丢
- 把每一步**摆到界面上**，用户看得见

## 二、核心设计思路

### 思路 1：每个 Bot 就是一个 DSH Session

这是整个项目最根本的一条。

```
Bot "小码" 的私聊     → 一个 root Session
Bot "小码" 在群 X     → 另一个 root Session
上下文满了换新段      → 又一个 Session（旧的仍可读）
```

**好处**：不重新实现 Agent 运行时。模型路由、工具审批、权限、日志、搜索，全部复用 DSH 已有的。项目只负责「组织」这一层，不碰「怎么跑模型」那一层。

**代价**：受 DSH 的 Session 语义约束，比如一段对话的上下文窗口是固定的。项目用「分段 + 保持身份」来化解——身份存在 `state.json` 里，不依赖某一具体 Session 存活。

代码体现：`index.js` 开头那段注释直接写明「Every Bot is one root Session」。

### 思路 2：任务归属是硬的，不是提示词求来的

README 里反复出现一句：**「用户最初联系的 Bot 拥有该任务」**。

这条不只是写进提示词让模型自觉，而是由**运行时状态 + 工具权限**保证的：

- 谁接到用户消息，任务就记在谁名下
- 派出去的活，结果自动回传到**发起者**，不能直接抛给用户
- 只有负责人能 `finish_bot_task`，其他人最多 `report_bot_task`
- 执行 Bot 说"我做完了"不算完成，负责人检查证据后才算

**为什么这样设计**：如果让执行 Bot 直接跟用户说"好了"，用户会失去全局视角——他问的是一件事，回来的却是一堆碎片。归属明确，用户永远只跟一个 Window 打交道。

### 思路 3：结果自己往上走，不需要谁去催

`handoffs.js` 开头的注释说得很清楚：

> Results find their way up by themselves, so no Bot needs to message one that waits for it, and that is the one hand-off refused.

翻译过来：**一个 Bot 在等另一个 Bot 的结果时，绝不允许它反过来去催。**

机制是：派活时挂起，结果回来时**自动唤醒**。所以：
- 不轮询
- 不重复发
- 不出现"A 问 B 进度、B 再问 C"这种套娃

### 思路 4：验收要过的关，是做出来的不是喊出来的

项目把「完成」拆成几个必须满足的条件：

```
report_bot_task（执行 Bot 报告）
  → 有没有结构化报告？  没有 → "待补报告"，退回
  → 有没有验证证据？    没有 → 退回
  → 产物在不在？        没有 → 退回
  → 所有委派都回来了吗？ 没有 → 不能验收
  → 所有问题都答了吗？   还有 → 不能验收
→ 负责人 finish_bot_task → 才算交付
```

`finish_bot_task` 在未结工作、未答问题、失败、结果不确定时**会拒绝执行**。这是代码级的拦截，不是建议。

### 思路 5：不确定就不重发

网络抖动、进程重启时，最容易犯的错是「消息可能没送到，那再发一次」。项目反过来：

> 不能确认送达时保留"不确定"，不盲目重复。

因为重复投递的代价可能是重复扣款、重复发布、重复导入——这些是真实的业务损失。宁可停在"不确定"让人工判断。

### 思路 6：状态落在磁盘上，重启能接上

`DSH_HOME/mek-bot/state.json` 存着：Bot 花名册、群、任务、问题、待发消息、偏好。

关键点是 **`state.lock` 文件锁**：防止两个 dsh 进程同时写同一个 state，互相覆盖。多标签页、多窗口时通过共享 feed 和心跳选举减少重复连接。

### 思路 7：和宿主共存，不做第二套 DSH

这是 fork 相对上游最大的取舍。

上游 DS-Bot 提供独立桌面端、移动端和插件三种形态。**这个 fork 只做插件**：

| 上游 | 本项目 |
|---|---|
| 全局 Bot 界面 + Bot 侧栏 | DSH 左侧只加**一个入口**，Bot 和群放顶部导航 |
| 有自己的完整 UI 体系 | 原生 React 组件接入公开 slots，CSS/弹窗限定在面板内 |
| 有自己的 Agent 模式切换 | Agent 从顶部列表打开 DSH 普通会话 |

README 里那句「无 iframe、无第二套 DSH」就是这个意思。

**为什么**：给用户减少割裂感，也避免两套 UI 状态互相打架。代价是要迁就 DSH 的界面约束，有些交互只能用近似方案（比如权限下拉框，现在是「跳到原生会话去设置」）。

## 三、架构

### 代码分布

```
ds-bot/
├── index.js          插件入口（80 行，装配各模块）
├── client.js         前端产物（2.2 万行，由 src/client 构建生成，不可手改）
├── mek.js            精简入口
├── src/
│   ├── host/         后端 67 个文件，2.2 万行
│   ├── client/       前端源码 105 个文件，约 2 万行
│   ├── office/       文档能力 9 个文件
│   └── shared/       共享工具
└── dev/              测试台、mock 模型
```

### host 层的关键模块

| 模块 | 职责 |
|---|---|
| `store.js` | state.json 读写、迁移、文件锁 |
| `roster.js` | Bot 花名册 |
| `groups.js` | 群聊（80KB，最大的模块） |
| `handoffs.js` | 派活、结果回传、自动唤醒 |
| `mek-coordination.js` | 任务协调、验收流程 |
| `tools.js` | 团队工具的注册与拦截 |
| `mek-safe.js` | 安全校验（凭据检测、危险内容拒绝） |
| `delivery.js` | 消息投递、去重 |
| `memory.js` | Bot 记忆（含只读约束） |
| `browser.js` | 每个 Bot 独立浏览器 |

### 双层防线的设计特点

项目里同一个约束通常在**两处**实现：

1. **提示词层**：写进 system prompt，让模型倾向于这样做
2. **运行时层**：工具执行时检查，违反就抛出 `bot/refused`

比如「不能用 `reply_to: user` 直接把结果抛给用户」——提示词会讲，工具调用时也会拒。

README 有一句很诚实的说明：

> 系统可以检查回报和证据是否齐全，但不保证真实模型一定正确执行或判断业务结果。

**这说明作者清楚：规则能约束形式，约束不了智慧。**

## 四、团队怎么运转（一次典型协作）

```
用户 ──→ 小音（主助手，任务负责人）
           │
           │ message_bot（派活，带目标/约束/验收标准）
           ↓
         小码（程序员）──ask_user──→ 问题回到小音
           │                          （不是直接问用户）
           │ report_bot_task（带证据）
           ↓
         小音 ──→ 小测（复查）
                  │
                  ↓
                结果回到小音 → finish_bot_task → 交付用户
```

关键点：

- **问题回流**：小码遇到要决定的事，问的是**负责人**。负责人能自己定的就定了，只有必须用户决定的才往上传。这样用户不会被一堆琐碎问题打断。
- **只有负责人能验收**：小音说完成才算完成。
- **对话不串**：用户单独找小码聊的内容，不会被小音看到，也不会自动归到主任务里。

### 群聊的特殊规则

群聊是多 Bot 协作的主场景：

- 群管理员**第一次** `message_bot` 派活时，自动保留主任务和原群入口
- 多级派工逐层回传，最后回到原管理员验收
- **讨论轮次结束 ≠ 任务完成**
- 普通 `@`、公告、闲聊**不自动建立任务**（避免每次聊天都生成一堆垃圾任务）

## 五、几个值得注意的设计决策

### 为什么禁掉 Bot 用 subagent

`tools.js` 里把 `subagent`、`subagent_codex`、`workflow` 等工具全部对 Bot 屏蔽：

```js
const DELEGATION_TOOLS = ['subagent', 'subagent_fork', 'subagent_codex', ...]
const DELEGATION_REFUSAL = 'Bots do not start subagents or workflows. ...'
```

注释给的理由：
1. **用户看不见也停不了**子 agent
2. **子 agent 会随启动它的那段对话结束**，而 Bot 对话是长跑的

这条是**这个项目的设计选择，不是 DSH 官方限制**。如果要放开，改一行就行，但会失去「用户可观察、可中断」这个保证。

### 为什么记忆是只读的

Bot 之间记忆互相只读，只有 Main Bot 能改别人的。理由跟任务归属一致：**不希望 Bot 互相改写对方的认知**，否则出问题时无法追溯是谁改的。

### 为什么不把任务当项目管

README 明确写：

> 用户无需创建项目或填写负责人。

这是刻意的低摩擦设计。让用户填一堆元数据，他就不想用了。归属和依赖由系统在交互过程中自动建立。

### 数据留在本机

团队、聊天、记忆全在 `DSH_HOME/mek-bot/` 下，不上传。这是明确的产品原则。

## 六、这个项目的边界（做和不做）

### 做

- Bot 团队的组织、派活、验收、交付闭环
- 任务和状态持久化
- 群聊协作
- 界面上的可见性（谁在做什么、进度、待决问题）
- 团队运营（策略、资源协调、项目事实、复用流程）

### 不做

- **不修改 DSH 本体**（AGENTS.md 硬规则第一条：只通过插件 API，缺什么就说，不许 patch）
- **不复刻上游的桌面端/移动端**（只做插件）
- **不实现第二套 Agent 运行时**（复用 DSH Session）
- **不保证模型判断正确**（只保证流程和证据齐全）
- **不做数据上传/云端同步**

### 三条硬规矩

从 AGENTS.md 摘的，对整个项目都成立：

1. **Build on DSH; never patch it** —— 用文档化的插件 API，不许改 DSH
2. **No secrets** —— 不写、不打印、不提交密钥；测试用 mock 模型
3. **Only original material** —— 不抄别人的代码和素材，兼容许可的要说清来源并记进 NOTICE

另外还有一条容易被忽略但很重要：

> **Do not touch the user's own DSH data.** 测试只能用 `.dsh-test-<name>/`，永远不指向 `~/.dsh`。

### 明确标注为「未完成」的部分

README 里如实写着的：

- 定时自动执行的**实际模型安排能力**仍需真实模型验收
- 规则编辑、未知结果的完整自助对账、完成后重开，**仍待补齐**
- Bot 面板**未接入** DSH 原生会话右侧栏
- 跨设备/浏览器的已读状态**不共享**
- Bot 既有历史**不会**在升级时自动重放

这种明确列缺口而非笼统说「已完成」的写法，本身就值得保持。

## 八、如果要参与开发

### 环境

```sh
cd ds-bot
npm ci            # 只装构建工具 esbuild
npm run harness   # 装测试用的 DSH 包（一次即可）
```

### 日常命令

```sh
npm run build                          # src/client → client.js
npm test                               # 单测；client.js 过期也会失败
node scripts/build-client.mjs --check  # 检查 client.js 是否同步
npm run lint                           # oxlint
```

**改完要同时提交 `src/client/` 和 `client.js`**，后者是生成物但必须入库。

### 分支规矩

- 从最新 `dev` 切出，命名 `feat/<issue>-<name>` / `fix/<issue>-<name>` / `docs/<name>`
- PR 提到 `dev`，不是 `main`
- **不许 rebase 已推送的分支，不许 force-push**

### 文档规矩（这条最特别）

AGENTS.md 里明确要求：

> **Every new feature, changed user flow, capability restriction or upstream adaptation must update its applicable documentation in the same change.**

即：**文档和代码必须同一次改动里更新**。而且要求 **Remove obsolete descriptions**——不是往上加新段落，是改掉过时的描述。

> A feature is not done while its documentation describes the old behavior.

功能没做完的定义之一，就是**文档还在描述旧行为**。这条标准挺高的，但能防止文档烂掉。

## 九、总结：这个项目真正的价值

它不是在做一个「更强的 AI」，而是在做**让 AI 干活变得可管理的基础设施**。

三件事它做得比较扎实：

1. **可见**——用户随时知道谁在做什么、卡在哪
2. **可追溯**——每个任务谁派的、谁做的、证据是什么，都留痕
3. **可中断**——用户能停、能改、能取消，而不是等一个黑盒跑完

至于 Bot 做得好不好，那是模型能力的事。这个项目负责的是：**不管做得好不好，你都看得见、管得住、找得到**。
